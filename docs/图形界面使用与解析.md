# rbm Go 版图形界面：使用手册与窗体系统解析

这份文档讲两件事：**怎么用**这个窗口，以及**它是怎么搭起来的**——每个控件对应 `internal/gui` 里
哪一段代码、点了之后数据往哪走。所有结论都对着代码行号和本机实测，不含推测。文中行号以
2026-10-16 这份代码为准，改动后请按符号名找。

配套阅读：`README.md`（构建、命令行、分区口径与参数校验）、`docs/选项说明.md`（① 那十一项各自
在说什么：「按时间分批」16 个选项的切法与规则、「桶内分组」四项的键怎么算、两个配角、高级参数）。
文中 `gui.go` 指 `internal/gui/gui.go`，其余路径同理。

## 1. 三十秒上手

1. 双击 `rbm.exe` → 窗口标题「回收站分批管理 rbm」，**没有黑色控制台窗口**（见 §10）。
2. **窗口一打开就自动扫描一次**，不用点任何按钮（见 §6）：同时弹一个非模态小提示窗「正在扫描，
   请等待完成…」，扫完自己关。日志区会打出用时、条目数、分区数，⑥ 那行进度文字留下
   「进度 空闲｜上次扫描用时 …」，④ 出现编号 1..N，⑤ 跟着显示编号 1 的清单。改了 ① 的参数再点
   【扫描 / 重扫 (F5)】重扫。
3. ③ 里选批次：要一整批就点【全选】（它跳过已经删完的分区），要逐个挑就在 ④ 最左列点方框
   （选中一行按空格也行）；**按住 Shift 再点另一个方框，两点之间（含两端）一起勾上**；
   也可以填「按编号勾选」`1-5,8-10,16` 点【应用】。
4. 单击 ④ 某一行 → ⑤ 列出这个分区里的元素（标题行写清编号/时间范围/组名/元素数/大小/
   index 区间/盘符）。
5. 两张表都能**点列名排序**：点一下升序、再点同一列降序，表头带箭头。
6. 点【预览删除（不动文件）】核对清单 → 没问题再点【⚠ 永久删除 N 个分区 / M 个条目】，
   在确认框里点【确认永久删除】这一个动作才会动手（见 §9）。

**删除是永久的**：直接从 `$Recycle.Bin` 抹掉 `$R` 数据与 `$I` 元数据，不经过回收站，删了就没了。

## 2. 窗体系统是什么

用的是 `github.com/lxn/walk`：**Win32 原生控件的 Go 绑定**，不是自绘界面，也不是 Web 壳。
每个控件背后都是一个真实的 HWND——分区表是 ListView（report 视图）、输入框是 EDIT、下拉是
COMBOBOX、分组框是 BUTTON(BS_GROUPBOX)、⑥ 那一行是原生进度条(msctls_progress32)、底部是只读文本
控件，主窗口带菜单和状态栏。
好处是外观、字体、DPI、键盘导航都跟系统一致，代价是只能跑在 Windows 上（本项目本来就只做
Windows）。

写法是 walk 的声明式子包：`gui.go` 用 `. "github.com/lxn/walk/declarative"` 点导入，所以
`MainWindow{ ... Children: []Widget{...} }` 这种嵌套字面量就是控件树本身，`AssignTo: &a.xxx`
把创建出来的控件指针回填到 `app` 结构体字段上，后续代码再拿它读写文本、刷新表格。
整棵树在 `gui.go:545` 的 `build()` 里一次建完，六个区块各由一个函数产出（`configBox` /
`resultBox` / `selectBox` / `tables` / `deleteBox` / `bottom`，见 §3）。启动自动扫描用的那个小提示窗
是最后一个 `walk.Dialog`（`showStartupNotice`，`gui.go:1004`），不属于这棵树。

**必须带 manifest。** `rbm.rc` 只有一行 `1 24 "rbm.manifest"`，把 `asInvoker` 权限、
`Microsoft.Windows.Common-Controls 6.0.0.0` 依赖和 `PerMonitorV2, system` DPI 声明编进 exe。
实测少了 `rsrc.syso` 时 `go build` 仍然成功，但一运行就退出码 1、stderr 打
`图形界面创建失败: TTM_ADDTOOL failed`——v6 通用控件只能靠 manifest 声明。

线程模型是 Win32 的标准做法：**界面只认主线程**。耗时动作（扫描、删除）丢进 goroutine，
算完用 `a.mw.Synchronize(func(){...})` 回到主线程更新控件（`startScan` 从 `gui.go:1184` 起，
删除的进度回调在 `gui.go:1449` 的 `deleteSelected` 里）。反方向的保护是 `beginBusy`（`gui.go:981`）：把 `a.lock` 里那
21 个控件（3 个动作按钮 + 12 个参数框/下拉 + 5 个选择与视图控件 + 【▼ 展开高级参数】按钮，清单在
`gui.go:605-609`）逐个
`SetEnabled(false)`，并置 `a.busy`，避免上一次任务没跑完又点一次（此时再点会只留一句
「上一次任务还在跑，请等它结束。」）。也正因如此，启动那个提示窗**必须是非模态**：`Dialog.Run()`
会把消息循环占住，扫描回来更新的 `Synchronize` 就永远排不上（注释在 `gui.go:1003`）。

`·` 普通、`✓` 成功（`ok`/`okf`）、`!` 警告（`warn`/`warnf`）、`×` 错误（`fail`/`failf`）。
多行正文的续行会缩进到正文列（`gui.go:897` 那个 `pad`），所以扫描那种一段段的输出读起来不歪。
`a.logLines` 跟着累加，标题旁的 logCount 就写「N 行」；【清空】`clearLog()`（`gui.go:940`）

所以级别靠字符前缀表达。

## 4. 表格的数据从哪来：模型 / 视图

walk 的 TableView 不存数据，数据由模型提供，界面只管按行列取值：

| 模型 | 位置 | 提供什么 |
| --- | --- | --- |
| `partModel` | `gui.go:217-406` | `RowCount`/`ColumnCount=9`/`Value(row,col)` 从 `[]*parts.Part` 按列号取字段；`checked map[int]bool` **按编号**存勾选；实现 `Sorter` + `ItemChecker` |
| `itemModel` | `gui.go:408-470` | `RowCount`/`ColumnCount=6`/`Value(row,col)` 从 `[]entry{全局index, *meta.Item}` 取值；同样实现 `Sorter` |

分区表 9 列的取值口径（`partModel.Value`，`gui.go:234`）：编号 `p.PID`｜时间范围 `p.TimeRange`｜
组名 `p.Label`｜元素数 `p.Count`｜大小 `tty.Human(p.Size)`｜index 区间 `p.IndexStart-p.IndexEnd`｜
盘 `p.Drives`｜剩余 `未删/总数`（`fmt.Sprintf("%d/%d", p.Count-p.Deleted, p.Count)`，
`gui.go:255`，所以这一列永远有数：13:27 那轮 daily 分批的 ④ 第 1 行有 721 个条目，一条没删时写
`721/721`，删完写 `0/721`，不是空档）｜
组内构成 `p.TopLabels`。
已删完的行整行变灰：`StyleCell`（`gui.go:809`）里判 `p.Deleted >= p.Count` 就把文字颜色设成灰色。

勾选框不是列，而是 `TableView{CheckBoxes: true}` 让 walk 给 ListView 加上 `LVS_EX_CHECKBOXES`
样式，它回调的是模型实现的 `ItemChecker` 接口：`Checked(row)` / `SetChecked(row, checked)`
（`gui.go:263-281`）。

### 4.1 点表头排序：唯一的开关是 `Sorter`

walk 在 `LVN_COLUMNCLICK` 里做的事是 `if sorter, ok := tv.model.(Sorter); ok && sorter.ColumnSortable(col)`
——**模型没实现 `Sorter` 就点不动**，本项目从没设过 `LVS_NOSORTHEADER`，所以表头一直是按得下去
的样子，只是要不要排序取决于模型。为此两个模型各嵌一份 `headerSort`（`gui.go:161-179`），它包一层
`walk.SorterBase`（提供恒真的 `ColumnSortable` 和发布事件的 `SortChanged`），自己只记
`SortedColumn()` / `SortOrder()`。`gui.go:152-156` 用三行编译期断言
（`_ walk.Sorter = (*partModel)(nil)` 等）把契约钉住：少实现一个方法，界面上只是「点了没反应」，
编译期先报错。

walk 给的语义是首次点某列 = 升序、再点同列 = 降序，`SortChanged` 一发布它就画表头箭头并重绘可见
行。排序本身走 `resortRows[T any]`（`gui.go:181`）+ `sort.SliceStable`，降序就是把 `less` 的两个
参数对调；每列的比较在 `partLess`（`gui.go:385`）/ `itemLess`（`gui.go:455`），主键相等时一律退回
编号或 index（`cmpStr`/`cmpInt`/`cmpF` 的后两个参数），所以同一列反复点不会乱跳。这几条由
`TestPartSortByColumn`、`TestItemSortByColumn` 直接对着模型断言（9 列 / 6 列各排一遍，外加
「同一列排两次结果一致」），不依赖窗口。

**排序只动显示顺序**：编号还是扫描时定下的编号，勾选也不清（见 §4.2）。③ 里原来那个「排序」
下拉框已经删掉——它调的是引擎层面的另一种排法（`engine.SortedParts`，会重建视图、因此清空勾选），
跟点表头重复，留着只会让人以为「不选它就没排序」。

### 4.2 勾选按编号记账，Shift 连选

`checked` 的键是**分区编号**（`PID`），不是视图行号。这是点表头排序的前置条件——按行号记的话，
重排一次勾选就漂到别的分区上了，而这是删除的选中集，漂了会删错东西。

`SetChecked`（`gui.go:271`）里问一次 `walk.ShiftDown()`（读 `GetKeyState(KeyShift)` 的符号位），
然后交给 `click(row, checked, shift)`（`gui.go:282`）：
- 普通点：只把这一行勾上/取消，并把这行的编号记成**锚点**；
- 按住 Shift 点：若已有锚点且不是同一个编号，用 `rowSpan`（`gui.go:310`）在**当前视图**里找到
  两个编号所在行的区间（小的在前，含两端），逐行标成同一个状态；锚点后移到这次点的行。

因为重排会把行的显示顺序打乱，区间按「当前视图里的行号」算，所以 Shift 连选勾的是**视觉上夹在
中间的那一批**，这正是拖选的习惯。两个编号有一个不在当前视图（被「只看未删完」筛掉了）就不连选，
只点那一个。这几条由 `TestShiftClickChecksInRange`、`TestPlainClickDoesNotSpan` 覆盖。

批量改完勾选后必须自己触发重绘：walk 的 `toggleItemChecked` 只对它自己点过的那一行发
`LVM_UPDATE`，区间里其余方框不会自己变。这里用 `refresh()`（`gui.go:366`）按当前排序再走一遍
`Sort`（`col` 为 -1 时不重排，只当事件发布用），让控件重读每行的 `Checked`。**不能用
`UpdateItem(i)`**：在实现了 `Sorter` 的模型上它会重排而不是重绘。

### 4.3 【全选】和【清空勾选】改的是同一个 map

`selectAlive()`（`gui.go:343`）遍历当前视图，跳过 `p.Deleted >= p.Count` 的分区，返回
「勾了几个 / 跳过几个」；`clearChecks()`（`gui.go:358`）把 `checked` 换成空 map、锚点复位 -1，
返回撤销了几个。两者都只改数据，重绘和文案由 `selectAll()`（`gui.go:1585`）/
`clearChecked()`（`gui.go:1608`）负责：`refresh()` → `updateSelectionHint()` → 按情况打一行日志。

【全选】为什么跳过已删完的分区：那些分区的 `$I`/`$R` 早就不在了，真删时 `engine.DeleteOne` 会
给它们的每一条都回一句「文件不存在」，几百行错误把日志刷满，反而盖掉真正要看的失败原因。跳过时
日志写成「已勾选当前视图的 N 个分区；另外 M 个已经没有未删条目，跳过了。」（`gui.go:1602`）
一个都没勾上时说的是「视图里 N 行全都已经删完了，一个也没勾…」（`gui.go:1598`）。
13:27 那轮（daily 分批、6 个分区全部还有内容）点到的是第三种：`✓ 已勾选当前视图的 6 个分区。`
测试：`TestSelectAliveSkipsEmptiedParts`、`TestClearChecksReportsPreviousSelection`。

数据换了一批（重新扫描、切「只看未删完」、真删收尾）时 `setRows`（`gui.go:376`）会重建
`checked`、把锚点复位成 -1、`reset()` 掉表头排序，再 `PublishRowsReset()` 让控件重画——
这就是「视图重建，勾选一律清空」的实现处。**点表头不在这条路径上**，它只调 `resort`。
`PublishRowsReset` 还会把当前行清成 -1，所以 `refreshParts` 在视图非空时补一句
`SetCurrentIndex(0)`（`gui.go:1174`），⑤ 才不会跟着空掉（实测：14:52 那轮自动扫描出 14 个分区，
一句没点，⑤ 的标题已经是「分区 1｜2026-10-16 12:52:00｜全部｜1 个 / 110.8KB｜index 1-1｜盘 G」）。

## 6. 一次扫描的完整路径

`startScan()`（`gui.go:1184`）：

1. `busy` 检查（顺带 `closeNotice()`，别让提示窗挂着）→ `collectOptions()` 取参数（参数错就地返回，
   不动快照，也照样关提示窗）。
2. 日志先写一行「开始扫描（全部盘，按自动找删除空档（默认）分批，单次上限 50000）…」
   （`gui.go:1212`）——中间那段是下拉当前项的中文显示名（`bucketDisplay[idx]`），选了「自定义」
   就直接用手填的写法；`beginBusy` 锁界面。
3. `go func(){ engine.Scan(o) → store.Write(dir, st) → store.WriteListCSV(dir, st) }()`，
   三段任何一段失败都只记 `err`，由主线程统一播报。
4. `Synchronize` 回主线程：`endBusy()` → `closeNotice()` → 失败就一行「扫描失败: …」；成功则
   `setState(st)` 刷表 + 状态栏，日志依次打「扫描完成（用时 …）：条目 N 个 / X，分区 M 个，
   编号 1..M」（`gui.go:1241`）、超限说明（若有）、异常记录前 5 条（若有，并注明全量在
   `scan_list.csv`）、两个产物路径、以及下一步提示「③ 里【全选】或点方框勾选 → ④ 单击看明细 →
   ⑥【预览删除】核对 → 再点【永久删除】并在弹窗里确认。」（`gui.go:1261`）同一个 `spent` 还会写进
   ⑥ 的进度文字（`gui.go:1235`）：「进度 空闲｜上次扫描用时 370ms」。

**扫到 0 个条目走的是同一支，不是失败分支**：`len(st.Parts) == 0` 时打的是
`✓ 扫描完成（用时 …）：条目 0 个、分区 0 个——回收站里当前用户没有对象。这是正常结果，不是错误；
没有可删的分区。`（`gui.go:1236-1239`），末尾那句下一步提示也换成「没有可删的分区。回收站清空之后
重新扫描会得到同样的 0。」（`gui.go:1259`）。级别前缀仍是 `✓`，因为快照照样正常写出去了。命令行那侧
对应 `scan` 退出码 0（见 README §4 的退出码表）。

**窗口一打开就自己跑一次这条路径**：`build()` 的末尾（`gui.go:615-616`）先
`updateSelectionHint()` 把概览摆好，再 `showStartupNotice()` 开提示窗，然后直接 `a.startScan()`。
这里**不读上次的 `state.json`**——界面要显示回收站此刻的内容，编号也按此刻内容重建；旧快照留在
磁盘上，命令行 `rbm parts` 之类照旧能读。

提示窗（`showStartupNotice`，`gui.go:1004`）是一个 `Dialog{...}.Create(a.mw)` + `Show()`，
**非模态**：`Run()` 会把消息循环占住，扫描回来更新的 `Synchronize` 就永远排不上。内容是一句
「正在扫描，请等待完成…」（`gui.go:1013`）加一个【关闭】按钮，标题「正在扫描回收站」，最小宽 360
逻辑像素。关闭有三条路，都走 `dlg.Close(0)`：扫完由 `closeNotice()`（`gui.go:1028`）关、用户点
【关闭】关、用户点标题栏 × 关；后两条会先经过 `dlg.Closing()` 上挂的回调把 `a.notice` 置 nil，
因为窗口一旦销毁句柄就不能再碰（`closeNotice()` 见到 nil 就什么都不做）。取证方式：起进程后用
`EnumWindows` 每 2ms 轮询该 PID 的可见顶层窗口（每轮只比类名、不发 `WM_GETTEXT`，实测一轮约 15ms，
第 24 轮抓着）。抓到的是类名 `\o/ Walk_Dialog_Class \o/`、标题「正在扫描回收站」的那个窗口，
rect `(1046,939)-(1586,1056)` = **物理** 540×117（这台机器 150% 缩放，脚本先调了
`SetProcessDPIAware` 才量的，所以是物理坐标；除以 1.5 = 逻辑 360×78，宽 360 正好等于 `MinSize`）。
它的子窗口 5 个：1 个 `Walk_Composite_Class`（可见）、2 行文本相同的 Static（`Walk_Static_Class`
与原生 `Static`，就是「正在扫描，请等待完成…」那一句）、1 个 `Walk_Spacer_Class`（不可见）、
1 个【关闭】按钮。6 秒后再数一遍，该 PID 可见的顶层窗口只剩 1 个（主窗口，物理 rect
`(266,266)-(2366,1674)` = 2100×1408），说明提示窗自己关了。它只在扫描那几百毫秒里存在，
轮询并非每次都能抓着——同一份构建，14:52 那轮用「每轮顺带 `WM_GETTEXT` 取标题」的慢脚本轮询
20 秒就没抓着（扫描 370ms），换成上面那个快脚本才在 14:53:47 抓着。

实测（2026-10-16 14:52:04 起窗口，14:52:05–14:52:06 扫完，本机回收站，默认参数，一个按钮都没点；
快照目录指到 `G:\tmp\rbm_ui_check\run2` 才起的窗口，所以覆写的是那个临时目录）：日志五行是


续行的缩进是 `emit` 补的（§3）。状态栏三段读作 `● 就绪`｜
`快照 2026-10-16 14:52:06｜条目 1528 个 / 276.1MB｜分区 14 个（编号 1..14）`｜
`未勾选分区｜未删完条目 1528 个`，⑥ 那行写 `进度 空闲｜上次扫描用时 370ms`，④ 出现 14 行、
⑤ 直接是编号 1 的概况（`分区 1｜2026-10-16 12:52:00｜全部｜1 个 / 110.8KB｜index 1-1｜盘 G`），

`<快照目录>\state.json` 与 `scan_list.csv` 覆写成此刻的回收站**。如果手上有一份想留给命令行
`show`/`delete` 用的旧快照，先展开【▼ 高级参数】把【快照目录】改成别的目录再打开，或者备份那个
`.rbm` 文件夹。

超限提示 `overflowText()`（`gui.go:1110`）是命令行同款文案：共有多少、上限多少、只建了其中
最老的多少个（按 `$I` 写入时间排序）、各盘「已扫/总数」，再给两条继续办法（调大上限一次看全 /
删一批再重扫）。**截断绝不静默**。

`setState`（`gui.go:1132`）写状态栏中段的格式串在 `gui.go:1135`。这一段的宽度只有 470 逻辑像素，
所以只放「快照时间｜条目｜分区」三项——早先还塞过「未删完 N」，实测会把文字挤到下一段
`sbHint` 上面去，删完一批之后要看未删完数字，看 ② 那行就好。

## 7. 明细联动与「看到的 = 要删的」

- 单击分区表某行触发 `CurrentIndexChanged`（`gui.go:611`）→ `showCurrentDetail()`
  （`gui.go:1288`）；双击走 `OnItemActivated`（`gui.go:808`），同一个函数。
- 明细数据来自 `entriesOf()`（`gui.go:1275`），它调的是
  `engine.SelectedParts(st, []int{pid}, prefix)` —— **和删除走的同一个函数**。所以「文件名前缀
  过滤」框里打的字会同时收窄明细和删除选中，你在表里看到多少条，删的时候就删多少条
  （元素数和大小是 `SelectedParts` 按 positions 逐条重算的，不是快照里声明的旧值）。
- 前缀框 `OnEditingFinished` 即时刷新明细；过滤到 0 条时标题写
  `分区 N｜…｜前缀过滤 "xyz" 之后 0 个`（`gui.go:1311`），明细清空但不报错。
- ⑤ 标题行的四种状态（`showCurrentDetail`）：没快照 → 「（还没有快照：点【扫描 / 重扫】）」；
  视图 0 行 → 「（视图里 0 个分区：去掉「只看未删完」或重新扫描）」；有行但没当前行 →
  「（还没点行：视图里有 N 个分区，单击任一行看它的条目明细）」；正常 → 那行分区的概况。
  后两种分开写，是因为重画表格会把当前行清成 -1（§4.3），此时视图明明有行，说「被
  「只看未删完」挡着」就是假信息。

## 8. 勾选、编号与四处概览

`updateSelectionHint()`（`gui.go:1619`）是唯一的出口：一次刷**四处**，不各自为政。下面四组是
本轮（2026-10-16 14:52:06，默认参数自动扫描，14 个分区 / 1528 个条目，一个按钮都没点）的实测读数：

- ② 的四个蓝色数字：分区 `14 个（编号 1..14）`、对象 `1528 个 / 276.1MB`、
  未删完 `1528 个条目 / 14 个分区`、已勾选 `0 个分区 / 0 个条目`。
  「未删完」按条目数（`st.AliveLeft()`，`store.go:95`）算，后面括号里那个是按分区数出来的
  （`Deleted < Count`），两个数不是一回事，所以都写出来。
- ⑥ 的按钮文案：`deleteButtonText(parts, items)`（`gui.go:84`）——没勾选是
  「⚠ 永久删除（未勾选分区）」（本轮实测），勾了是「⚠ 永久删除 N 个分区 / M 个条目」，13:27 那轮
  全选后确认框里同规模的写法是 `6 个分区 / 774 个条目，约 139.1MB`。规模随时可见，
  就不会出现「以为只删了一个桶、实际删了整站」。测试 `TestDeleteButtonTextCarriesScale`。
- ④ 的概览行 `partsHint`：`当前视图 14 行｜快照共 14 个分区（编号 1..14）｜未删完条目 1528 个
  （在 14 个分区里）｜勾选 0 个分区 / 0 个条目 0B`。
- 状态栏右侧 `sbHint`：没快照时是「F5 扫描；勾选分区后先预览再删除」，没勾选时本轮是
  「未勾选分区｜未删完条目 1528 个」，勾了就是「已勾选 N 个编号 / N 个分区 / M 个条目 大小」，
  真删时改成「删除中 n/N  已删 x  失败 y」（`gui.go:1496`）。状态栏是 `msctls_statusbar32`，
  分段文字取不利索：对整个控件发 `WM_GETTEXT` 只回第一段（本轮实测回的是「● 就绪」），
  按段发 `SB_GETTEXT` 四段全回空串，所以中段和右段的字是截窗口底部那条读出来的。

它被 `SetChecked`、`applyIDs`、`selectAll`、`clearChecked`、`refreshParts`、`build()` 都调到，
所以点方框、Shift 连选、按编号勾、全选、清空、切筛选、扫描完成这几种情况下概览都不会滞后。
`partsHint` 那一行同时是 §3 里说的「和明细表标题配平的一行」。

- `checkedSelection()`（`gui.go:1322`）把勾选的编号（`checkedPIDs()`，`gui.go:332`，直接对 map 的
  键排序，所以与显示顺序无关）交给 `engine.SelectedParts` 得到实际会删的分区 `chosen`
  （含前缀收窄，可能为空）。
- 【应用】走 `applyIDs()`（`gui.go:1540`）：`tty.ParseIDs(spec, len(st.Parts))` 解析
  `1-5,8-10,16`，越界会直接报错；能解析但当前视图里没有的编号，会照勾能勾的，然后补一句
  「已勾选 N 个分区；编号 X 不在当前视图里（被「只看未删完」或分区上限挡着了），需要的话先取消
  筛选。」勾完调 `partModel.refresh()` 整表重画，不是只刷一行。
- 「只看未删完」切换走 `onAliveToggled()`（`gui.go:1180`）→ `refreshParts(true)`，`explain=true`
  时把 `aliveFilterText()`（`gui.go:93`）那句解释打进日志。这条文案专门解决一个反馈：刚扫完的
  快照里没有任何「已删完」的分区，勾上它一行都不会少，看上去就像复选框坏了。所以那种情况下说的是
  「只看未删完：已开启（只显示还有未删条目的分区）。本快照里还没有「已删完」的分区（N 个分区
  全部还有内容），所以视图行数不变。删完一批之后再开，就能看到已清空的分区从列表里消失。」
  ——本轮快照 14 个分区全部还有内容（④ 那行概览写的就是「未删完条目 1528 个（在 14 个分区里）」），
  正是这一支的适用情形（`hidden == 0`）。真的隐藏了东西时改说数字：
  「只看未删完：…。快照 N 个分区，隐藏已删完 H 个，视图 S 行。」（两个分支都在 `gui.go:99-104`，
  测试 `TestAliveFilterTextExplainsWhyRowsDidNotChange`。）

## 10. 双击不出现黑色控制台窗口

可以，而且现在默认构建就做到了。机制在 `gui.go:532` 的 `Run()`：界面 `build()` 成功之后、
进消息循环之前调一次 `FreeConsole`（`gui.go:540`）——`x/sys v0.33.0` 没导出这个函数，所以
`gui.go:28` 用 `syscall.NewLazyDLL("kernel32.dll").NewProc("FreeConsole")` 按名字取入口，
返回值不接（本来就没有控制台时调用失败，忽略即可）。

exe 仍是控制台子系统（本轮读 PE 头量过：`rbm.exe` 的 Subsystem 字段 = 3），所以命令行分支的输出
照旧回到终端；只有走 GUI 分支时才把系统为双击新建的那个控制台放掉。实测（2026-10-16 14:52:04，
本机 150% 缩放，`Start-Process` 起进程（等价于双击：控制台是系统新建的），快照目录指到临时目录
`run2`）：起窗口后第 3 秒枚举该 PID 的顶层窗口，**顶层 11 行、可见的只有 1 个**——
`\o/ Walk_MainWindow_Class \o/`，`size=1400x939`；其余 10 行全是 `vis=False` 的
`tooltips_class32`（5 个）、`ComboLBox`（3 个，下拉列表的隐藏容器）、`MSCTFIME UI`、`IME`；
按类名筛 `Console` 命中 **0 个**，也就是没有任何控制台窗口属于它；也没有多出来的
`\o/ Walk_Dialog_Class \o/`，说明启动提示窗扫完即关（本轮自动扫描 370ms，第 3 秒时它早就关了；
抓着它的那次见 §6）。同一个主窗口先搬到 `(0,0)`（级联位置会把下缘推出屏幕）再量两次：非 DPI 感知的
脚本量到 `(0,0)-(1400,939)`，同一脚本调完 `SetProcessDPIAware` 再量是 `(0,0)-(2100,1408)`——
同一个窗口的两套口径，`GetWindowRect` 给谁看取决于**调用方**感不感知 DPI，所以文档里出现
1400×939 和 2100×1408 两个数字别当成窗口变了大小。最后对主窗口发 `WM_CLOSE`，3 秒内进程退出，
临时目录里生成了 `state.json`、**没有** `ledger.csv`；全程没碰仓库那份 `.rbm\ledger.csv`
（时间戳仍是取证前的 12:44:10）。

三个附带行为，说清楚免得误会：

- **从终端里直接运行 GUI，终端仍然会等到进程退出。** 本轮实测（14:56:40，用 `Start-Job` 跑
  `& rbm.exe`，等价于在终端里直接敲）：8 秒后那个 job 还是 `Running`；对唯一的
  `Walk_MainWindow_Class` 窗口发 `WM_CLOSE`，调用方立刻返回（14:56:49 打出 `returned`，整程 9 秒）
  ——`FreeConsole` 只丢控制台所有权，不改变父进程对进程句柄的等待。想在终端里继续敲命令，
  用 `start rbm.exe` 或者干脆用命令行子命令。
- 双击时控制台可能闪一下（系统先建、程序再放掉）。如果一点都不能闪，就编一个纯图形产物：
  `go build -ldflags "-H windowsgui" -o rbm-gui.exe .`（本轮实测这份的 Subsystem 字段 = 2，
  控制台从头就不存在）。这份也能当命令行用：本轮实测
  `rbm-gui.exe parts --state-dir G:\tmp\rbm_ui_check\run\.rbm` 与 `rbm.exe parts --state-dir …`
  同一份快照各跑一次，两份都返回码 0、各 18 行（参数行 + 合计行 + 表头 + 分隔线 + 14 个分区行），
  `cmp` 判一字不差。
- 窗口创建失败时错误仍然看得到：`FreeConsole` 在 `build()` 成功之后才调，失败路径的
  `图形界面创建失败: …`（`gui.go:535`）还是打到 stderr 再返回 1（`gui.go:536`）。

| 【永久删除】是灰的 | 只有一种情况：上一次扫描或删除还在后台跑（`beginBusy` 把 `a.lock` 里那 21 项一起置灰，含这个按钮）。**没勾选时它不灰**，只是文案变成「⚠ 永久删除（未勾选分区）」，点下去不会弹确认框，只打一句「没有勾选分区：…」（`gui.go:1464-1466`） |
| 【永久删除】点了没删 | 看是不是被保险丝拦下（日志有错误行 + 「未做任何改动。」），或在确认框点了【取消】 |
| 刚勾的选没了 | 重新扫描、切「只看未删完」、真删收尾，这三种都会重建视图并清空勾选（日志提示「视图换了，原先勾选的 N 个分区已经取消勾选」），这是防止删错批次。**点表头排序不清空**——勾选按编号记账（§4.2） |
| 【全选】勾的数字比视图行数小 | 视图里有已经删完的分区，它们被跳过了，日志会说明跳了几个（§4.3） |
| Shift 点第二个方框却没连选 | 两种情况只勾你点的那一个：① 这是本次第一个方框（还没有锚点，`anchor = -1`）；② 两点之间某个编号不在当前视图里（被「只看未删完」筛掉了），`rowSpan` 不成立 |
| 点列名没反应 | 分区表/明细表都实现了 `walk.Sorter`（编译期断言在 `gui.go:152-156`），正常一定排；如果某次改动后失效，先看模型是否还满足该接口 |
| 提示「上一次任务还在跑，请等它结束。」 | 上一次扫描/删除还在后台跑，控件此时也是灰的；等它结束 |
| 编号 X 勾不上 | 该编号在当前视图里被筛掉了，日志会点名；取消「只看未删完」或调大分区上限再来 |
| 删除有失败项 | 明细看日志（最多 20 条），全量在 `ledger.csv` 的「结果」列；常见是文件被占用或权限不足 |

## 13. 与内核的边界（为什么 GUI 里没有算法）

`gui` 包只 import 了 `engine`/`meta`/`parts`/`store`/`tty` 五个内部包，自己不做任何分区或删除判定：
分区在 `engine.Scan`+`parts.BuildPartitions`，选分区与前缀收窄在 `engine.SelectedParts`，
删除与账本在 `engine.RunDelete`，快照读写在 `store`。界面拿到的永远是这些函数返回的结构。
好处不只是少写代码：GUI 与命令行共用同一份 `state.json`、同一套编号，所以 ④ 里看到的每个数字
都能被 `rbm parts` 原样复现（§6 末尾那组实测就是两边对照的结果），命令行也能接着 GUI 的快照
继续 `show`/`delete`。
