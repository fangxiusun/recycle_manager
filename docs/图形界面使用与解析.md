# rbm Go 版图形界面：使用手册与窗体系统解析

这份文档讲两件事：**怎么用**这个窗口，以及**它是怎么搭起来的**——每个控件对应 `internal/gui` 里
哪一段代码、点了之后数据往哪走。所有结论都对着代码行号和本机实测，不含推测。

配套阅读：`README.md`（构建、命令行、与 Python 版的对齐证据）。文中 `gui.go` 指
`internal/gui/gui.go`，其余路径同理。

---

## 1. 三十秒上手

1. 双击 `rbm.exe` → 窗口标题「回收站分批管理 rbm」，**没有黑色控制台窗口**（见 §10）。
2. **窗口一打开就自动扫描一次**，不用点任何按钮（见 §6）。日志区会打出用时、条目数、分区数，
   左边表格出现编号 1..N。改了上面的参数再点【扫描 / 重扫 (F5)】重扫。
3. 单击左边某一行 → 右下方明细表列出这个分区里的元素（标题行写清编号/时间范围/组名/元素数/
   大小/index 区间/盘符）。
4. 在最左列点方框勾选要删的分区（选中一行按空格也行）；**按住 Shift 再点另一个方框，两点之间
   （含两端）一起勾上**；要一次勾一批就在「按编号勾选」填 `1-5,8-10,16` 点【应用】。
5. 两张表都能**点列名排序**：点一下升序、再点同一列降序，表头带箭头。
6. 点【预览删除（不动文件）】核对清单 → 没问题再点【永久删除勾选的分区】并在确认框里点「是」。

**删除是永久的**：直接从 `$Recycle.Bin` 抹掉 `$R` 数据与 `$I` 元数据，不经过回收站，删了就没了。

## 2. 窗体系统是什么

用的是 `github.com/lxn/walk`：**Win32 原生控件的 Go 绑定**，不是自绘界面，也不是 Web 壳。
每个控件背后都是一个真实的 HWND——分区表是 ListView（report 视图）、输入框是 EDIT、下拉是
COMBOBOX、分组框是 BUTTON(BS_GROUPBOX)、底部是进度条 + 只读文本控件，主窗口带菜单和状态栏。
好处是外观、字体、DPI、键盘导航都跟系统一致，代价是只能跑在 Windows 上（本项目本来就只做
Windows）。

写法是 walk 的声明式子包：`gui.go` 用 `. "github.com/lxn/walk/declarative"` 点导入，所以
`MainWindow{ ... Children: []Widget{...} }` 这种嵌套字面量就是控件树本身，`AssignTo: &a.xxx`
把创建出来的控件指针回填到 `app` 结构体字段上，后续代码再拿它读写文本、刷新表格。
整棵树在 `gui.go:430` 的 `build()` 里一次建完。

**必须带 manifest。** `rbm.rc` 只有一行 `1 24 "rbm.manifest"`，把 `asInvoker` 权限、
`Microsoft.Windows.Common-Controls 6.0.0.0` 依赖和 `PerMonitorV2, system` DPI 声明编进 exe。
实测少了 `rsrc.syso` 时 `go build` 仍然成功，但一运行就退出码 1、stderr 打
`图形界面创建失败: TTM_ADDTOOL failed`——v6 通用控件只能靠 manifest 声明。

线程模型是 Win32 的标准做法：**界面只认主线程**。耗时动作（扫描、删除）丢进 goroutine，
算完用 `a.mw.Synchronize(func(){...})` 回到主线程更新控件（`gui.go:807` 起）。反方向的保护是
`beginBusy`（`gui.go:656`）：把 `a.lock` 里那 18 个控件（3 个按钮 + 11 个参数框 + 4 个筛选控件，
清单在 `gui.go:474`）逐个 `SetEnabled(false)`，并置 `a.busy`，避免上一次任务没跑完又点一次
（此时再点会只留一句「上一次任务还在跑，请等它结束。」）。

左右两块的结构是刻意配平的：**每个 GroupBox 里都是「一行 TextLabel + 一张表」**。左表现在多了
一行概览标签 `partsHint`（内容见 §8），它和右边明细表的标题行同高，两张表的表头才落在同一条
水平线上。实测（本机显示缩放 150%，窗口左上角 (190,190)）两个 `SysListView32` 的 rect 顶边
都是 `y=727`：分区表 `(232,727)-(1424,1110)`、明细表 `(1466,727)-(2248,1110)`，两个表头也都
是 `y=727..752`；把窗口高度拉到 1590 或压到 990 物理像素，两条顶边依旧同为 727。

左右两张表在 `HSplitter` 里按 3:2 分宽（两个 GroupBox 的 `StretchFactor`），中间可以拖；竖向的
多余空间几乎全给这块表格（`bottom()` 那层没有设 `StretchFactor`，日志区靠最小高 120 撑住），
所以窗口拉大时变的是表，不是日志。
分区表第 3 列的标题不是写死的：`refreshParts` 会按快照参数改成「路径组」或「前缀组」
（`gui.go:796`，取名规则在 `store.go:87` 的 `GroupCol()`：`by == "dir"` 叫路径组，其余叫前缀组）。

日志区有个 Windows 特有的小坑：编辑控件只认 CRLF 才换行，所以 `log()`（`gui.go:642`）把每个
`\n` 换成 `\r\n` 再 `AppendText`，然后 `ScrollToCaret()` 滚到底。

## 4. 表格的数据从哪来：模型 / 视图

walk 的 TableView 不存数据，数据由模型提供，界面只管按行列取值：

| 模型 | 位置 | 提供什么 |
| --- | --- | --- |
| `partModel` | `gui.go:145-311` | `RowCount`/`ColumnCount=9`/`Value(row,col)` 从 `[]*parts.Part` 按列号取字段；`checked map[int]bool` **按编号**存勾选；实现 `Sorter` + `ItemChecker` |
| `itemModel` | `gui.go:313-375` | `RowCount`/`ColumnCount=6`/`Value(row,col)` 从 `[]entry{全局index, *meta.Item}` 取值；同样实现 `Sorter` |

分区表 9 列的取值口径（`partModel.Value`，`gui.go:164`）：编号 `p.PID`｜时间范围 `p.TimeRange`｜
组名 `p.Label`｜元素数 `p.Count`｜大小 `tty.Human(p.Size)`｜index 区间 `p.IndexStart-p.IndexEnd`｜
盘 `p.Drives`｜剩余 `未删/总数`（`fmt.Sprintf("%d/%d", p.Count-p.Deleted, p.Count)`，所以这一列
永远有数：本机当前快照里那个 70 个条目的分区显示 `70/70`，删完就是 `0/70`，不再是空档）｜
组内构成 `p.TopLabels`。
已删完的行整行变灰：`StyleCell`（`gui.go:580`）里判 `p.Deleted >= p.Count` 就把文字颜色设成灰色。

勾选框不是列，而是 `TableView{CheckBoxes: true}` 让 walk 给 ListView 加上 `LVS_EX_CHECKBOXES`
样式，它回调的是模型实现的 `ItemChecker` 接口：`Checked(row)` / `SetChecked(row, checked)`
（`gui.go:193-208`）。

### 4.1 点表头排序：唯一的开关是 `Sorter`

walk 在 `LVN_COLUMNCLICK` 里做的事是 `if sorter, ok := tv.model.(Sorter); ok && sorter.ColumnSortable(col)`
——**模型没实现 `Sorter` 就点不动**，本项目从没设过 `LVS_NOSORTHEADER`，所以表头一直是按得下去
的样子，只是要不要排序取决于模型。为此两个模型各嵌一份 `headerSort`（`gui.go:88-143`），它包一层
`walk.SorterBase`（提供恒真的 `ColumnSortable` 和发布事件的 `SortChanged`），自己只记
`SortedColumn()` / `SortOrder()`。`gui.go:79-86` 用三行 `var _ walk.Sorter = (*partModel)(nil)`
把契约钉在编译期：少实现一个方法，界面上只是「点了没反应」，编译期先报错。

walk 给的语义是首次点某列 = 升序、再点同列 = 降序，`SortChanged` 一发布它就画表头箭头并重绘可见
行。排序本身走 `resortRows[T any]`（`gui.go:111`）+ `sort.SliceStable`，降序就是把 `less` 的两个
参数对调；每列的比较在 `partLess`（`gui.go:291`）/ `itemLess`（`gui.go:361`），主键相等时一律退回
编号或 index（`cmpStr`/`cmpInt`/`cmpF` 的后两个参数），所以同一列反复点不会乱跳。

实测（本机，点分区表「大小」列名）：第一下升序，头几行是 `0B / 0B / 56B / 120B`；第二下降序，
变成 `588.1MB / 401.4MB / 133.3MB`，表头箭头跟着翻。明细表 6 列同理。

**排序只动显示顺序**：编号还是扫描时定下的编号，勾选也不清（见 §4.2）。下拉框「排序」是引擎
层面的另一种排法（`engine.SortedParts`，会重建视图、因此清空勾选），和点表头是两回事。

### 4.2 勾选按编号记账，Shift 连选

`checked` 的键是**分区编号**（`PID`），不是视图行号。这是点表头排序的前置条件——按行号记的话，
重排一次勾选就漂到别的分区上了，而这是删除的选中集，漂了会删错东西。

`SetChecked`（`gui.go:201`）里问一次 `walk.ShiftDown()`（读 `GetKeyState(KeyShift)` 的符号位），
然后交给 `click(row, checked, shift)`（`gui.go:212`）：
- 普通点：只把这一行勾上/取消，并把这行的编号记成**锚点**；
- 按住 Shift 点：若已有锚点且不是同一个编号，用 `rowSpan`（`gui.go:240`）在**当前视图**里找到
  两个编号所在行的区间（小的在前，含两端），逐行标成同一个状态；锚点后移到这次点的行。

因为重排会把行的显示顺序打乱，区间按「当前视图里的行号」算，所以 Shift 连选勾的是**视觉上夹在
中间的那一批**，这正是拖选的习惯。两个编号有一个不在当前视图（被「只看未删完」筛掉了）就不连选，
只点那一个。

批量改完勾选后必须自己触发重绘：walk 的 `toggleItemChecked` 只对它自己点过的那一行发
`LVM_UPDATE`，区间里其余方框不会自己变。这里用 `refresh()`（`gui.go:272`）按当前排序再走一遍
`Sort`（`col` 为 -1 时不重排，只当事件发布用），让控件重读每行的 `Checked`。**不能用
`UpdateItem(i)`**：在实现了 `Sorter` 的模型上它会重排而不是重绘。

实测（本机，120 行的分区表）：点第 1 行方框 → 只有编号 1 勾上；再按住 Shift 点第 5 行方框 →
编号 `1 / 11 / 8 / 10 / 120`（这五行当时的显示顺序）方框全部勾上，概览行同步写成
「勾选 5 个 / 4089 个条目 1.3GB」。

数据换了一批（重新扫描、切「只看未删完」、换下拉框排序）时 `setRows`（`gui.go:282`）会重建
`checked`、把锚点复位成 -1、`reset()` 掉表头排序，再 `PublishRowsReset()` 让控件重画——
这就是「视图重建，勾选一律清空」的实现处。**点表头不在这条路径上**，它只调 `resort`。

## 5. 参数区怎么变成引擎入参

`collectOptions()`（`gui.go:698`）把界面拼成 `engine.Options`，GUI 不自己算分区：

| 控件 | 落到 | 默认 | 备注 |
| --- | --- | --- | --- |
| 时间桶 | `Bucket` | 空 | 空 = 按删除时间断点自动切区（gap）；可填 `daily`/`hourly`/`monthly`/`3mo`/`30m`/`gap:5m`/`auto` |
| 桶内分组 | `By` | `dir` | 下拉显示中文，取值走 `byValues = dir/prefix/ext/token` 的序号映射 |
| 目录层级 | `DirLevel` | `2` | `levelValues = 1/2/3/full` |
| 前缀长度 | `PrefixLen` | 3 | `by=prefix/token` 时必须 ≥ 1，否则报「「前缀长度」在 prefix 分组下至少 1 个字符」 |
| 桶数上限 | `MaxBuckets` | 12 | |
| 分区上限 | `MaxParts` | 120 | 调小会把小组并成「其他」 |
| 小组并入 | `MinCount` | 5 | |
| 限定盘符 | `Drives`/`DrivesSpec` | 空=全部 | `store.SplitDrives` 解析逗号分隔 |
| 单次扫描上限 | `MaxScan` | 50000 | 0 = 不限 |
| 删除保险丝 | 单独返回 `fuse` | 0 | 不进 `Options`，只传给删除 |
| 快照目录 | `StateDir` | `<当前目录>\.rbm` | 留空回落到默认（`a.dir()`） |

数字框统一走 `intValue()`（`gui.go:682`）：留空取默认值，非整数回一句
`「前缀长度」要填整数，现在填的是 "abc"`，负数回 `「分区上限」不能是负数，现在填的是 -3`。
这些错误只打进日志区，不会弹窗，也不会改界面上已填的其他值。

## 6. 一次扫描的完整路径

`startScan()`（`gui.go:807`）：

1. `busy` 检查 → `collectOptions()` 取参数（参数错就地返回，不动快照）。
2. 日志先写一行「开始扫描（全部盘，单次上限 50000）…」，`beginBusy` 锁界面。
3. `go func(){ engine.Scan(o) → store.Write(dir, st) → store.WriteListCSV(dir, st) }()`，
   三段任何一段失败都只记 `err`，由主线程统一播报。
4. `Synchronize` 回主线程：`endBusy()` → 失败就一行「扫描失败: …」；成功则 `setState(st)`
   刷表 + 状态栏，日志依次打「扫描完成（用时 …）：条目 N 个 / X，分区 M 个，编号 1..M」、
   超限说明（若有）、异常记录前 5 条（若有，并注明全量在 `scan_list.csv`）、
   两个产物路径、以及下一步提示。

**窗口一打开就自己跑一次这条路径**：`build()` 的末尾（`gui.go:482-485`）先写一行日志
「rbm 图形界面：窗口一打开就按当前回收站自动扫描一次，参数改完点【扫描 / 重扫】(F5)。」，
再 `updateSelectionHint()` 把概览行摆好，然后直接 `a.startScan()`。这里**不读上次的
`state.json`**——界面要显示回收站此刻的内容，编号也按此刻内容重建；旧快照留在磁盘上，
命令行 `rbm parts` 之类照旧能读。实测：双击起窗口、一个按钮都没点，状态栏就写成了
`快照 2026-10-15 21:44:04｜条目 17402 个 / 1.8GB｜分区 120 个（编号 1..120）｜未删完 17402`，
左边表格 120 行（`LVM_GETITEMCOUNT` 实测 120）。

一个要提前知道的后果：自动扫描走的是和点按钮完全相同的那条路径，所以**打开窗口就会把
`<快照目录>\state.json` 与 `scan_list.csv` 覆写成此刻的回收站**。如果手上有一份想留给命令行
`show`/`delete` 用的旧快照，先把【快照目录】改成别的目录再打开，或者备份那个 `.rbm` 文件夹。

超限提示 `overflowText()`（`gui.go:746`）是命令行同款文案：共有多少、上限多少、只建了其中
最老的多少个（按 `$I` 写入时间排序）、各盘「已扫/总数」，再给两条继续办法（调大上限一次看全 /
删一批再重扫）。**截断绝不静默**。

`setState`（`gui.go:768`）写状态栏的格式串在 `gui.go:771`，就是上面那行 `快照 …｜条目 …｜
分区 …｜未删完 …`。

## 7. 明细联动与「看到的 = 要删的」

- 单击分区表某行触发 `CurrentIndexChanged` → `showCurrentDetail()`（`gui.go:884`）；双击走
  `OnItemActivated`，同一个函数。
- 明细数据来自 `entriesOf()`（`gui.go:871`），它调的是
  `engine.SelectedParts(st, []int{pid}, prefix)` —— **和删除走的同一个函数**。所以「文件名前缀
  过滤」框里打的字会同时收窄明细和删除选中，你在表里看到多少条，删的时候就删多少条
  （元素数和大小是 `SelectedParts` 按 positions 逐条重算的，不是快照里声明的旧值）。
- 前缀框 `OnEditingFinished` 即时刷新明细；过滤到 0 条时标题写
  `分区 12｜…｜前缀过滤 "xyz" 之后 0 个`，明细清空但不报错。
- 没有快照时标题是「（还没有快照：点【扫描 / 重扫】）」；有快照但当前视图被筛空时是
  「（当前视图里没有可选的分区；换掉「只看未删完」或重新扫描）」。

## 8. 勾选、编号与两处概览

- `checkedSelection()`（`gui.go:912`）把勾选的编号（`checkedPIDs()`，`gui.go:262`，直接对 map 的
  键排序，所以与显示顺序无关）交给 `engine.SelectedParts` 得到实际会删的分区 `chosen`
  （含前缀收窄，可能为空）。
- 【应用】走 `applyIDs()`（`gui.go:1086`）：`tty.ParseIDs(spec, len(st.Parts))` 解析
  `1-5,8-10,16`，越界会直接报错；能解析但当前视图里没有的编号，会照勾能勾的，然后补一句
  「已勾选 N 个分区；编号 X 不在当前视图里（被「只看未删完」或分区上限挡着了），需要的话先取消
  筛选。」勾完调 `partModel.refresh()`（`gui.go:1119`）整表重画，不是只刷一行。
- 【清空勾选】`clearChecked()`（`gui.go:1129`）把 `checked` 换成空 map、锚点复位 -1，再 `refresh()`。
- `updateSelectionHint()`（`gui.go:1138`）一次刷**两处**：
  - 左表上方的概览行 `partsHint`：`当前视图 120 行｜快照共 120 个分区（编号 1..120）｜未删完
    17402 个｜勾选 5 个 / 4089 个条目 1.3GB`（实测截图里的这一行，勾选数随点随变）；
  - 状态栏右侧 `sbHint`：没快照时是「F5 扫描；勾选分区后先预览再删除」，没勾选时是
    「未勾选分区｜未删完 N 个」，勾了就是「已勾选 3 个编号 / 3 个分区 / 412 个条目 25.3MB」。

  它被 `SetChecked`、`applyIDs`、`clearChecked`、`refreshParts`、`build()` 都调到，所以点方框、
  Shift 连选、按编号勾、切筛选、扫描完成这五种情况下概览都不会滞后。`partsHint` 那一行同时是
  §3 里说的「和明细表标题配平的等高一行」。

## 9. 三层删除闸门在界面上的落点

| 层 | 界面 | 代码 | 等价命令行 | 不通过时的表现 |
| --- | --- | --- | --- | --- |
| 1 预览 | 【预览删除（不动文件）】 | `previewDelete` `gui.go:938` | `delete <编号> --dry-run` | 只把选中统计表（`deleteSummary` `gui.go:966`，表头/列宽与命令行一致）灌进日志、明细灌进右表，末尾一句「预览未做任何改动」 |
| 2 确认 | 【永久删除勾选的分区】弹 Yes/No | `deleteSelected` `gui.go:989`，弹框在 `gui.go:1028` | `delete <编号> --yes` | 默认按钮是**「否」**（`MsgBoxDefButton2`）、警告图标；点否 → 日志「已取消，未做任何改动。」 |
| 3 保险丝 | 「删除保险丝」填 N | `engine.RunDelete` 的 `max` | `delete <编号> --max N` | 选中条目数 > N 时整批不动；日志打错误 + 「未做任何改动。」 |

确认框正文（格式串在 `gui.go:1017`）会把条目数、大小、编号列表、前缀、快照目录都列出来，填进去
像这样（数字是示意）：

```
将永久删除 412 个条目，约 25.3MB。

这些内容直接从 $Recycle.Bin 抹掉，不进回收站、无法恢复。
选中分区编号：12,13,14（前缀 log*）
快照：G:\...\rbm_go\.rbm\state.json

建议先点【预览删除】核对清单。现在确定要删吗？
```

第 3 层的判定发生在打开账本之前（`internal/engine/engine.go:213` 的 `max` 检查在
`store.OpenLedger` 之前），所以被保险丝拦下时 `ledger.csv` 连创建都不会有。

真删的进度与结果：`engine.RunDelete` 每处理 100 条回调一次（`progressEvery`），主线程把进度条
`SetValue(n)` 并把状态栏写成「删除中 320/412  已删 318  失败 2」（数字为示意，格式串固定）。收尾在 `finishDelete()`
（`gui.go:1054`）：打「完成：删除 N 个，失败 M 个，账本 …」，失败明细最多列 20 条（多的注明
「…另有 X 条失败记录，见账本」），然后提示「快照已更新（标记了本次删掉的条目，编号不变）」
「要看回收站最新状态请重新扫描」，最后 `refreshParts()`（`gui.go:789`，在 `gui.go:1083` 调用）
重画——它走 `setRows`，勾选被清空、表头排序也复位，需要重新勾。

## 10. 双击不出现黑色控制台窗口

可以，而且现在默认构建就做到了。机制在 `gui.go:417` 的 `Run()`：界面 `build()` 成功之后、
进消息循环之前调一次 `FreeConsole`（`gui.go:425`）——`x/sys v0.33.0` 没导出这个函数，所以
`gui.go:29` 用 `syscall.NewLazyDLL("kernel32.dll").NewProc("FreeConsole")` 按名字取入口，
返回值不接（本来就没有控制台时调用失败，忽略即可）。

exe 仍是控制台子系统（PE subsystem=3），所以命令行分支的输出照旧回到终端；只有走 GUI 分支时
才把系统为双击新建的那个控制台放掉。实测（本机，`Start-Process` 起一个新建控制台的进程，等价
于双击）：3 秒后枚举该进程的可见顶层窗口，**只有 1 个**——`1400x860 @101,101` 的
「回收站分批管理 rbm」，没有任何控制台窗口属于它。

三个附带行为，说清楚免得误会：

- **从终端里直接运行 GUI，终端仍然会等到进程退出。** 实测在 pwsh 里 `& rbm_fc.exe`，pwsh 等了
  143 秒直到界面被关掉——`FreeConsole` 只丢控制台所有权，不改变父进程对进程句柄的等待。想在
  终端里继续敲命令，用 `start rbm.exe` 或者干脆用命令行子命令。
- 双击时控制台可能闪一下（系统先建、程序再放掉）。如果一点都不能闪，就编一个纯图形产物：
  `go build -ldflags "-H windowsgui" -o rbm-gui.exe .`（PE subsystem=2，控制台从头就不存在）。
  这份也能当命令行用：实测 `cmd /c` 调它跑 `parts`，同样被等待、返回码 0、输出 124 行。
- 窗口创建失败时错误仍然看得到：`FreeConsole` 在 `build()` 成功之后才调，失败路径的
  `图形界面创建失败: …` 还是打到控制台再退出（返回码 1）。

## 11. 菜单里另外两项

- **文件 → 打开快照目录**：`openStateDir()`（`gui.go:1162`）先 `MkdirAll` 再
  `ShellExecute("open")`，用资源管理器打开当前快照目录；失败只写日志。
- **帮助 → 使用说明**：`usageText`（`gui.go:51`）的全文弹窗（`gui.go:1186`）。里面是 5 步流程
  （自动扫描 → 单击看明细 → 勾选/Shift 连选/按编号勾 → 预览 → 永久删除）加一段「两张表都可以点
  列名排序，只动显示顺序」的说明，与本文 §1 的 6 条是同内容的两种写法。
- **帮助 → 关于 rbm**：`showAbout()`（`gui.go:1189`）现算本机盘符，报「本机盘符 N 个（C,D,…）」和内核一句话说明。

## 12. 排查表

| 现象 | 原因 / 处理 |
| --- | --- |
| 双击后一闪就没了 | 多半是缺 `rsrc.syso`：命令行里运行看 stderr，出现 `图形界面创建失败: TTM_ADDTOOL failed` 就按 README §2 第 1 步补资源文件 |
| 打开窗口后要等一会儿才有内容 | 正常：GUI 一打开就**自动扫描**当前回收站（§6），扫描期间参数区、三个按钮和筛选控件都是灰的，日志区会先打「开始扫描…」再打「扫描完成（用时 …）」。此时表格是空的，不是坏了 |
| 打开窗口显示的和我上次看到的对不上 | 设计如此：启动**不载入旧快照**，编号按此刻回收站内容重建。要回到某次结果，用命令行 `rbm parts`（读 `state.json`）或重新扫描一次 |
| 命令行 scan 完，GUI 里还是旧数据 | 两边读的是同一个 `state.json`，但 GUI 只在「打开时」和「点【扫描 / 重扫】」时刷新；点一下按钮即可。顺便确认两边【快照目录】填的是同一个目录 |
| 【永久删除】点了没删 | 看是不是被保险丝拦下（日志有错误行 + 「未做任何改动。」），或确认框点了「否」（默认按钮就是「否」） |
| 刚勾的选没了 | 重新扫描、换下拉框「排序」、切「只看未删完」、真删收尾，这四种都会重建视图并清空勾选（日志提示「分区表已刷新，勾选已清空」），这是防止删错批次。**点表头排序不清空**——勾选按编号记账（§4.2） |
| Shift 点第二个方框却没连选 | 两种情况只勾你点的那一个：① 这是本次第一个方框（还没有锚点，`anchor = -1`）；② 两点之间某个编号不在当前视图里（被「只看未删完」筛掉了），`rowSpan` 不成立 |
| 点列名没反应 | 分区表/明细表都实现了 `walk.Sorter`（编译期断言在 `gui.go:82-86`），正常一定排；如果某次改动后失效，先看模型是否还满足该接口 |
| 提示「上一次任务还在跑，请等它结束。」 | 上一次扫描/删除还在后台跑，控件此时也是灰的；等它结束 |
| 编号 X 勾不上 | 该编号在当前视图里被筛掉了，日志会点名；取消「只看未删完」或调大分区上限再来 |
| 删除有失败项 | 明细看日志（最多 20 条），全量在 `ledger.csv` 的「结果」列；常见是文件被占用或权限不足 |

## 13. 与内核的边界（为什么 GUI 里没有算法）

`gui` 包只 import 了 `engine`/`meta`/`parts`/`store`/`tty` 五个内部包，自己不做任何分区或删除判定：
分区在 `engine.Scan`+`parts.BuildPartitions`，选分区与前缀收窄在 `engine.SelectedParts`，
删除与账本在 `engine.RunDelete`，快照读写在 `store`。界面拿到的永远是这些函数返回的结构。
这也是 `README.md` §5 里那组比对能成立的原因：GUI 与命令行共用同一份 `state.json`、同一套编号，
Python 版也能直接打开它（实测两边 `parts` 读 Go 写的快照，124 行输出 0 行不同）。
