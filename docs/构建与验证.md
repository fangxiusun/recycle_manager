## 2. 本地构建

### 2.1 环境与依赖

本机实测：Go 1.24.5、`CGO_ENABLED=0`、`GOTOOLCHAIN=local`，依赖只有 `go.mod` 里四个：
`github.com/lxn/walk`、`github.com/lxn/win`、`github.com/mattn/go-runewidth`、
`golang.org/x/sys`（都是纯 Go，无需 C 工具链，只有下面第 1 步的资源编译需要 `windres`）。

### 2.2 三步

在仓库根目录直接跑 `build.bat`（一次产出两份），或者手工按下面三步来：

```bat
:: 0) 一键：build.bat 就是把下面三步串起来，任何一步失败即 exit 1
build.bat

:: 1) 生成界面资源（必须在主包目录，产物 1228 字节）
windres --input=rbm.rc --input-format=rc --output=rsrc.syso --output-format=coff

:: 2) 编译：控制台子系统（PE subsystem=3），命令行用这份
set CGO_ENABLED=0&& set GOTOOLCHAIN=local&& go build -o rbm.exe .

:: 3) 纯图形版，进程从头就不创建控制台（PE subsystem=2），双击用这份
go build -ldflags "-H windowsgui" -o rbm-gui.exe .
```

## 3. 发布流水线（`.github/workflows/release.yml`）

### 3.1 触发与两个 job

- 触发：**推 `v*` tag** 才会建 GitHub Release；`workflow_dispatch`（手动）走同一套构建，产物只进
  Artifacts，不建 Release——免得凭空造 tag。**推 `main` 不跑这个 workflow。**
- `test` job 在 **windows-latest**：`internal/gui` 依赖 `lxn/walk` 与 `golang.org/x/sys/windows`，
  两者的文件都带 `//go:build windows`，换到 Linux 主机上连编译都过不去。步骤是 checkout → setup-go →
  gofmt → `go vet ./...` → `go test -count=1 ./...`。
- `build` job 在 **ubuntu-latest**（`needs: test`）：`CGO_ENABLED=0` 的 Go 本来就能 `GOOS=windows` 交叉
  编译，唯一要 C 工具链的是资源文件，而 Linux 上装一个 apt 包就够，Windows runner 上反而没有现成的
  `windres`。步骤是 定版本号 → 装 windres → 生成 `rsrc.syso` → 编两份产物（带 `-trimpath`）→
  校验 PE 头与 manifest 并写发布说明 → 打包 → 上传 Artifacts → 发 Release。
- `permissions: contents: write`、`concurrency: group=release, cancel-in-progress=false`，
  `env` 里固定 `GO_VERSION=1.24.5`、`CGO_ENABLED=0`、`GOTOOLCHAIN=local`。
- 三个 action 的版本按 2026-10-16 各自主仓库 README 的写法取：`actions/checkout@v7`、
  `actions/setup-go@v7`、`actions/upload-artifact@v7`。

### 3.2 `windows-latest` 的 autocrlf 与 `.gitattributes`

GitHub 的 Windows runner 把 `core.autocrlf` 设成 `true`，没有归一化规则时 checkout 出来的 `.go` 全带
CRLF，`gofmt -l internal/` 会把 16 个文件一并报出来——2026-10-16 首次跑 CI 就是这么红的，代码本身没有
格式问题。修法是在根目录加 `.gitattributes`（32 行）：`.go .mod .sum .md .yml .yaml .json .py .rc
.manifest` 以及 `.gitignore`/`.gitattributes` 自己走 LF，`.bat`/`.ps1` 走 CRLF，
`internal/meta/testdata/isample/*` 和 `*.syso *.exe *.zip` 标 `-text`（二进制，别做换行符转换——
那 15 个 `$I` 样例是按字节比对的）。验证方式不是在工作目录里 `git add --renormalize`，而是**用带
autocrlf 的全新克隆**去检一遍（`git checkout-index -a -f` 会跳过 stat cache 没变的文件，测不出真实
检出结果）：`9b1e92e` 那一轮报 16 个脏文件，加完属性的全新克隆报 0 个。

### 3.3 时区不能跟着 runner 走

第二个 CI 红在 `internal/parts` 的 Python 样例比对（`TestMatchesPythonFixture`）：runner 不是 UTC+8，
`time_range` 整块差一天。要点是 **Go 在 Windows 上忽略 `TZ` 环境变量**，所以本地 `TZ=UTC go test` 复现
不了；修法不是跳过，而是把比对钉在样例自己的时区上：`parts_test.go` 的 `fixtureZone` 用样例里成对的
`(epoch, deleted_at)` 反推偏移（`offset = ceil(wallUnix − epoch)`），把 `meta.LocalTZ` 换成那个
`time.FixedZone` 再跑，另加一条 `TestFixtureComparisonIgnoresMachineZone` 把机器时区换成 UTC 再全量
比一遍，专门复现 CI 场景。2026-10-17 01:33 这一轮重读 `py_parts.json`：**5 个数据集合计 1 400 个条目
（300/300/300/250/250），反推出的偏移只有一个值 = +28800；配置 49 组（11/11/11/8/8）**，`go test -v`
里两条用例各打一行 `49 组配置与 python 结果一致`。

### 3.4 windres 的包名

`ubuntu-latest` 现在是 Ubuntu 24.04（noble）。装的是
`binutils-mingw-w64-x86-64`（`--no-install-recommends`），它提供
`/usr/bin/x86_64-w64-mingw32-windres`；`mingw-w64` 那个 metapackage 只依赖 `g++-mingw-w64`/
`gcc-mingw-w64`，用不上还要多装一堆编译器。脚本按
`WINDRES="$(command -v x86_64-w64-mingw32-windres || command -v windres)"` 取路径，写进 `$GITHUB_ENV`
给下一步用。

### 3.5 版本号走 step output

定版本号的步骤 `id: ver`，同时写 `$GITHUB_ENV` 和 `$GITHUB_OUTPUT`：产物名出现在 `with:` 的表达式里，
而 GitHub 的文档只保证 `env` 上下文装的是 workflow/job/step 的 `env:` 键，`$GITHUB_ENV` 写进去的变量
归到哪个上下文没写死，所以 `${{ steps.ver.outputs.VER }}` 才是要依赖的那一份。推 tag 用
`$GITHUB_REF_NAME`，手动触发用 `dev-<短 sha>`。

### 3.6 字节层校验与发布说明

`校验 PE 头与内嵌 manifest` 那一步跑一段 python3：对 `dist/rbm.exe`、`dist/rbm-gui.exe` 读
`e_lfanew`/`opt_magic`/`Subsystem`/`Microsoft.Windows.Common-Controls` 命中次数/SHA-256，
不是 `0x020B`、找不到 manifest 行、或 Subsystem 不等于期望值（3 和 2）就 `sys.exit` 让 CI 变红；
顺带把结果写成发布说明里的表。**CI 只做到字节层校验，Linux runner 跑不了 PE，「双击真能开界面」这一步
还需要人工点一次。**

### 3.7 打包与校验文件

`cp README.md README.en.md LICENSE THIRD-PARTY-NOTICES.txt dist/` →
`cd dist && zip ../rbm-${VER}-windows-amd64.zip rbm.exe rbm-gui.exe README.md README.en.md LICENSE THIRD-PARTY-NOTICES.txt`
→ `rm dist/` 下那四个副本，所以 zip 里的成员名是**不带目录的**。带两份 README 是因为默认门面是中文，
解压目录里得给英文用户留入口；带许可文本是 MIT 的分发要求。**这一段是 2026-10-17 改的，v1.0.1 那份
zip 里还只有 `rbm.exe`/`rbm-gui.exe`/`README.md` 三个成员**（§4），下一次发版才是上面这套。
`sha256sum` 那一步用的是 `dist/rbm.exe` 这种带前缀的路径，所以 `rbm-${VER}-sha256.txt` 里两行 exe 的
**文件名带 `dist/` 前缀**，和 zip 里的成员名不一致——比对时按哈希值对齐，别按名字。这是已知的小瑕疵，
下次发版前加一句 `cd dist` 就好（还没改）。

### 5.2 选项全集

`scan -h` 里的九个分区参数（`--bucket --max-buckets --by --dir-level --prefix-len --max-parts
--min-count --drives --max-scan`）在 GUI 参数区一一对应（控件→字段的映射表在
`docs/图形界面使用与解析.md` §5，每个选项在说什么见 `docs/选项说明.md`）。写法支持 `--name v`、
`--name=v`、`-name`、布尔开关 `-v`，选项和位置参数可以混写，`--` 之后全当位置参数。其余选项按
`-h` 原文：

- `scan`：`--bucket 文本`（不填=按删除时间断点自动切区，也可 `minutely/hourly/daily/weekly/monthly/
  30m/15m/1h/3d/2mo`、`gap:5m`、`auto`）、`--max-buckets N`（默认 12）、
  `--by dir|prefix|ext|token`（默认 `dir`）、`--dir-level N|full`（默认 2）、`--prefix-len N`（默认 3）、
  `--max-parts N`（默认 120）、`--min-count N`（默认 5）、`--drives C,G`、
  `--max-scan N`（默认 50000，0 = 不限）、`--state-dir 目录`（默认 `当前目录\.rbm`）
- `parts`：`--alive`、`--sort time|size|count`
- `show`：`--start N --end N`、`--prefix 串`、`--limit N`（默认 40，0 = 全部）、`--tail`（从尾部
  数着显示）、`--local`（序号换成分区内序号从 1 数，默认显示的是全局 index）
- `delete`：`--dry-run` / `--yes`、`--prefix 串`、`--max N`（保险丝）、`--sample N`（默认 15）、
  `--every N`（默认 200 刷一次进度）、`-v`
- 所有命令：`--state-dir 目录`、`--lang zh|en`（界面语言，见 §5.6）

### 5.3 shell

**shell** 是给「几万条要删一上午」准备的：进去先 `scan` 一次，之后的 `show`/`delete` 都用内存里
这份快照，编号不会因为你删了一批就漂走。会话命令是 `scan / parts / show / delete / info /
help / quit|exit|q|退出`。提示符带着当前快照的规模，本机 2026-10-16 13:57 实测是
`rbm[13:31:50 快照 774条/9区 剩774]> `（方括号里是快照时间）；用 `--no-scan` 进去时内存里还没有快照，头一个提示符
是光秃秃的 `rbm> `，等某条命令把快照读进来之后才开始带规模。会话里没写 `--state-dir` 的命令自动
沿用启动时那个目录。`--no-scan` 跳过启动扫描（只读旧快照）。

### 5.4 退出码

`0` 成功 / 取消 / dry-run / **扫到 0 个条目**；`1` 数据或运行错误（没有快照、编号越界、
时间桶写法不认、指定盘上没有当前用户的回收站目录）；`2` 用法错误、未确认删除、或踩了保险丝。
本机 2026-10-16 13:55~13:58 的实测（快照是 774 条目 / 9 个分区那份；保险丝那两条打在一份**假路径**
的快照副本上，真实回收站一个字节都没动）：

| --- | --- | --- |
| `delete 1-2 --dry-run` | 0 | 「未做任何改动。确认无误后加 --yes 执行真删除。」 |
| `delete 999` | 1 | 「编号 999 超出范围 1-9」 |
| `show 0` | 1 | 「编号 0 超出范围 1-9」 |
| `delete 1 --sample 5`（不带 `--yes`） | 2 | 「这是不可逆操作。加 --yes 明确确认后再执行…」 |
| `delete 2 --max 1 --yes` | 2 | 「条目数 17 超过 --max 1，已中止。可分区分批删。」（此时账本文件都不会被创建） |
| `parts --sort bad` | 2 | 「rbm parts: error: 选项 --sort 的取值无法识别: bad」 |

### 5.5 产物三件套

都在快照目录里：`state.json` 快照本体；`scan_list.csv` 本次快照的全量清单，带 UTF-8 BOM、CRLF 行尾，
Excel 双击即开；`ledger.csv` 删除账本，每删一条追加一行（操作时间/编号/index/删除时间/字节/盘/文件名/
原路径/结果），只在真删时创建。**GUI 一打开就自动扫描**，走的是与点按钮同一条路径，所以会把
`<快照目录>\state.json` 和 `scan_list.csv` 覆写成此刻的回收站；想留住某份旧快照给命令行
`show`/`delete`，先把【▼ 高级参数】里的快照目录改到别处，或备份那个 `.rbm` 文件夹。

### 5.6 界面语言（中 / 英）

**优先级**（`internal/i18n/i18n.go:41` 的 `SetEnv`）：命令行 `--lang` > 环境变量 `RBM_LANG` >
`%LOCALAPPDATA%\rbm\settings.json` 里的 `"language"` 字段 > 中文。认不出的写法**逐级往下退，不报错打断
使用**；`Parse`（`i18n.go:93`）认 `zh` / `en` 和常见的地区写法（`zh-CN`、`cn`、`中文`、`en-US`、
`english`…）。`RBM_SETTINGS_FILE` 能把配置文件的落点改到别处——测试和试验都用它，别拿真配置当草稿纸。

`--lang` 对两份 exe 都有效，而且是**先定语言、再决定走命令行还是走图形界面**（`main.go:14`：
`SplitLangArgs` → `i18n.SetEnv` → 参数空了才 `gui.Run()`），所以 `rbm.exe --lang en` 不带子命令
就是直接开英文界面。

**命令行双语对照**（2026-10-17 10:49 那一份快照：9955 个条目 / 407.3MB / 120 个分区，`--state-dir`
指到临时目录，两轮读的是同一个 `state.json`）。数字、编号、index 区间逐行一致，只有界面文字换了：

| 位置 | 中文 | 英文 |
| --- | --- | --- |
| `parts` 首行 | `快照时间 2026-10-17 10:49:31  参数 {…}` | `Snapshot 2026-10-17 10:49:31  options {…}` |

| `parts` 表头 | `编号 时间范围 路径组 元素数 大小 index区间 盘 剩余 组内构成/示例` | `ID Time range Path group Items Size Index range Drive Left Contents` |

## 6. 分区口径、参数校验与耗时

这几条是从 `$I` 元数据到编号之间的取舍，看代码时容易踩，都写在这里：

- **时间桶的非法写法直接拒绝，退出码 1**，不会静默改变分区结果。本机实测：`0m`/`0h`/`0d`/`0mo`/`5x`
  → `无法识别的时间桶: …（可用 minutely/hourly/daily/weekly/monthly/Nm/Nh/Nd/Nmo/auto/gap[:30m]）`；
  `gap:0m` → `粒度必须大于 0: 0m`；`gap:abc` → `无法识别的粒度单位 "c"（只能用 s/m/h/d）`。
  合法写法：`minutely hourly daily weekly monthly 3mo 30m gap:5m auto`。
- **不可表示的删除时间**按「元数据损坏」处理：FILETIME 换算出的 epoch 落在
  `[86400, 32536713599]` 秒（约 1970-01-02 至 3001-01-18，`internal/meta/meta.go:162`）之外就判掉，
  正常删除时间不可能落在外面。这类条目单独成组并写进异常记录，不会混进正常分区。
- **时区**在启动时取当前 UTC 偏移构造 `time.FixedZone`（`internal/meta/meta.go:55`）。本机
  `TimeZoneKeyName = China Standard Time`、`GetTimeZoneInformation` bias = −480 且无夏令时，
  所以时间范围渲染与本机一致；跨夏令时的历史条目会被按当前偏移解释（见 §9）。CI 上这份偏移不固定，
  所以样例比对钉在样例自己的时区上（§3.3）。
- **原路径只有一个盘符**（`D:`）时取不到文件名，`baseName`（`internal/meta/meta.go:217`）返回空串，
  display 退回 `$I` 文件名的尾巴，不会显示成空行。
- **`state.json` 是紧凑 JSON**，并把 `<` `>` `&` 转义成 `\u003c` 等（`json.Marshal` 默认行为）。
  本机 774 条的快照写出来 351,893 字节，`scan_list.csv` 196,946 字节（2026-10-16 13:45 实测）。
- **`--state-dir` 走 `filepath.Join` 归一化**，`G:/tmp/x` 会写成 `G:\tmp\x\scan_list.csv`。
- **扫到 0 个条目不是错误**：`Scan`/`BuildState` 照样落盘（空快照 + 空清单），命令行返回 0 并解释
  两句，GUI 走 `gui.go:1318` 那句「这是正常结果，不是错误」。仍然报错的是**指定盘上根本没有当前
  用户的回收站目录**（`--drives e` → 退出码 1）。详见 `docs/选项说明.md` §6。

**耗时**（本机真实回收站，774 条目 / 139.1MB / 9 分区，2026-10-16 13:45 各跑三轮）：`scan`（全量
元数据解析 + 分区 + 写两份产物）265 / 315 / 193 ms；`parts`（读快照重列）62 / 55 / 59 ms。也就是说
首次解析元数据是主要开销，只读快照的命令在 0.06 s 上下（瓶颈在快照文件本身）。GUI 自动扫描同一批
条目的实测是 830ms（2026-10-16 13:24:38 那一轮，从界面日志读出），比同一台机器上手敲的 `scan` 慢一些；
两边都只报自己的用时。**这一段和 §5.4 那张退出码表都是 2026-10-16 那几轮的记录，2026-10-17 这一轮
没有重跑**：回收站内容随时在变，重跑就是另一份数字，不属于同一轮，不能混着引。

## 7. 数据怎么读

`internal/meta` 是唯一的元数据入口：枚举 `GetLogicalDrives` 掩码里的盘符，定位当前用户 SID 名下的
`$Recycle.Bin\<SID>`，按 `$I` 文件的写入时间排序后决定是否截断（`--max-scan`），再把 `$I`/`$R`
配对成条目。`internal/parts` 只吃条目列表，产出 `bounds`（时间边界）和 `parts`（分区，含编号），
不碰文件系统。所以「换个分组维度重排编号」不需要重新扫描回收站。

### 8.2 测试不碰真实回收站

测试只用自建的假 `$I` 文件和临时目录：假回收站走 `meta.BinDir{Drive:"Z",Path:tmp}` 这类注入，
不经命令行（`--drives` 只认真实盘符），所以永远不会删到真实条目，也不会覆盖谁的 `.rbm`。
`internal/gui` 的用例更窄：只直接调模型的排序/勾选方法和几个纯函数（按钮文案、下拉写法表与
`parts.ParseSpec` 的一致性、编号简报、筛选解释、分组方式到参数显隐的映射），既不建窗口也不碰文件。

不建窗口的代价是**表格重绘这类 Win32 绘制行为写不成用例**：`TableView.Invalidate()` 要有真的 ListView
句柄才有意义，无窗口的模型测试里既调不到也没法断言。所以 11:44 那一轮修的「删除完不立刻变灰、要鼠标逐行
划过才显形」没有配套测试，验证走的是真机 A/B：把修复前的 `gui.go` 单独编一份二进制留档，同一套探测脚本
（点一次只改数据不改列名的控件，然后按 26 物理像素的行带比对截图）分别跑两份产物，看「改动落地那一刻」
和「鼠标划过之后」的行带差值各出现在哪一份。以后谁把 `setPartRows`/`setItemRows` 换回直接 `setRows`，
单测不会红，只有这条真机路径能重新发现它——想加回归测试的话，得先让 `internal/gui` 有用例能建窗口。

### 8.3 黄金样例与时区口径

`internal/{meta,parts,store}/testdata/` 下的 `py_*.json` 是三份**合成数据黄金样例**（假路径、固定
种子，不含任何真实回收站内容），2026-10-17 01:29 重读大小：`py_meta.json` 3 140 字节、
`py_parts.json` 1 118 187 字节、`py_state.json` 63 253 字节。`meta` 的样例还配了 `testdata/isample/`
里 15 个 `$I` 原件（在 `.gitattributes` 里标了 `-text`，别让换行符转换碰它们），Go 测试读同一批字节
逐字段比对。测试只读这些 JSON/`$I` 文件本身，**`go test` 全程不需要 Python，也不依赖本仓库之外的
任何东西**。

样例里的日期串是**打快照那台机器**（UTC+8）的本地时刻，所以时区相关的比对不能跟着 runner 的时区走
（§3.3）：`py_parts.json` 用样例自带的 `(epoch, deleted_at)` 反推出偏移（`parts_test.go` 的
`fixtureZone`，本轮重读：1 400 个条目的偏移全部是 +28800）并把 `meta.LocalTZ` 钉住再跑，另有一条用例
把机器时区换成 UTC 复现 CI 的场景；`py_meta.json` 里则直接记了生成时的偏移
（`local_utc_offset_now`），比对测试发现它和当前时区不一致就跳过时区相关断言——**这条还是跳过口径**，
非 +8 的机器上 `meta` 的时区断言实际没被验证，和 `parts` 的做法不一致，属于已知待办。

同目录的 `regen_py_*.py` 是这三份样例最初生成时用的脚本，它们会把仓库外的
`../../../../recycle_manager` 加进 `sys.path` 再 import 那个实现的模块 —— 那套代码**不在本仓库**，
所以克隆下来的人跑不了这些脚本，也不需要跑。只有在原参考实现还在上述相对位置时才可能重新生成，
而重跑会覆写 `py_*.json` 和 `isample/`（`regen_py_meta.py` 里有 `shutil` 清理），真要再生成请先
确认这三份文件在当前测试里仍然是绿的。

## 9. 已知限制

- 只看当前用户 SID 名下的 `$Recycle.Bin\<SID>`，不处理别的 SID 目录，也不处理 `$R` 缺 `$I` 的孤儿
  （这类会在异常记录里点名，本次不动）。
- 盘符来自 `GetLogicalDrives` 的 A–Z 掩码；`--drives` 只接受真实存在的盘符字母。
- 时间分区按本机时区渲染。Go 侧是启动时的固定偏移，跨夏令时的历史条目会被按当前偏移解释
  （见 §6 第 3 条）。
- 界面与命令行是**中英双语**，但只有这两种，且中文是默认；`README.md` 另有一份英文版
  `README.en.md`，而 `docs/` 下的详解（含本轮新增的索引、路线图、已知问题）只有中文。GUI 里切语言
  只换「从这里开始」的文字，日志区已经写下的那几行保持写下时的语言（见 `docs/图形界面使用与解析.md` §11）。
- 落盘的东西不跟着语言走：`state.json` 的字段名与取值、两个 CSV 的中文表头、账本「结果」的「已删」、
  分组标签（「全部」「其他」「元数据损坏」「特殊位置」「(根)」「(无扩展名)」）。这是有意的，理由见 §5.6。
- 编号只在当前快照内有效：重新扫描会按当时内容重新编号，已删完的条目不会再出现。
- 单次扫描默认最多 5 万条，超出时只取最老的那些建快照，并把「共多少、取了少、各盘已扫/总数、
  两条继续办法」写清楚，绝不静默丢弃；`--max-scan 0` 为不限。
- 删除是永久的：直接抹掉 `$R` 数据与 `$I` 元数据，不经过回收站，删了就没了。请配合
  【预览删除】/`--dry-run` 和「删除保险丝」/`--max` 使用，明细永远在 `scan_list.csv`，
  每一笔结果都在 `ledger.csv`。
- 许可证：仓库里是 **MIT**（`LICENSE`，版权行写 `Copyright (c) 2026 rbm contributors`），
  六个依赖的许可证全文见 `THIRD-PARTY-NOTICES.txt`。这份声明是手工维护的，没有生成脚本、也没有
  CI 的一致性检查，改依赖时记得同步（见 §1）。
- 发布物的小瑕疵：`sha256.txt` 里两行 exe 带 `dist/` 前缀而 zip 成员名不带（§3.7）；
  「双击下载包里的 `rbm-gui.exe` 真能开界面」还没有人工验证记录（§4）。
- 上面这些「用起来会撞到」的东西在 [已知问题](known-issues.md) 里按类别重讲了一遍，面向使用者；
  本节面向改代码和发版的人，两边如有出入以本节 + 源码为准。
